I need to modify the existing Airflow Intake Agent UI and backend to support creating multiple DAG entries from a single intake request.

Current behavior

The current intake form is designed for a single DAG and has these steps:

1. Requester & Jira Information
2. Scheduling & Configuration
3. DAG Information
4. Airflow Task Argument Details

All fields are currently mapped individually to backend variables, and the Python script uses those mapped values to generate the intake form/output.

New requirement

A single Jira/request should be able to contain multiple DAG definitions.

The requester/Jira information is common to the entire request and should be entered only once.

The DAG-specific information must be repeatable based on the number of DAGs the user wants to create.

⸻

1. Step 1 — Requester & Jira Information

Keep the following fields as request-level/common fields:

* Requester Name
* Jira Number
* Fix Version
* Description
* Jira Date
* Target Environment

Add a new field:

* Number of DAGs to Create

Example:

Number of DAGs to Create: 3

This value determines how many DAG configuration sections are dynamically created.

These requester/Jira fields must NOT be duplicated for every DAG.

⸻

2. DAG-specific information

Everything related to an individual DAG must be grouped under that DAG.

For each DAG, include the existing fields currently present in:

* Scheduling & Configuration
* DAG Information
* Airflow Task Argument Details

The exact existing fields and their current behavior should be preserved unless a change is required to support multiple DAGs.

The structure should conceptually become:

Request
│
├── Requester/Jira Information
│
├── DAG 1
│   ├── Scheduling & Configuration
│   ├── DAG Information
│   └── Airflow Task Argument Details
│
├── DAG 2
│   ├── Scheduling & Configuration
│   ├── DAG Information
│   └── Airflow Task Argument Details
│
└── DAG N
    ├── Scheduling & Configuration
    ├── DAG Information
    └── Airflow Task Argument Details

⸻

3. UI/UX requirement

Do NOT simply render all DAG sections one below another because the page could become extremely long when the user enters 5, 10, or more DAGs.

Use a clean, minimal UI such as expandable/collapsible DAG cards or an accordion.

For example:

Requester & Jira Information
[completed/common information]
Number of DAGs to Create: 3
DAG Configurations
┌──────────────────────────────────────┐
│ ▼ DAG 1                              │
│                                      │
│ DAG Name:                            │
│ Request Type:                        │
│ Schedule:                            │
│ Scheduling Configuration:            │
│ Task Information:                   │
│ Task Arguments:                     │
│                                      │
└──────────────────────────────────────┘
┌──────────────────────────────────────┐
│ ▶ DAG 2                              │
└──────────────────────────────────────┘
┌──────────────────────────────────────┐
│ ▶ DAG 3                              │
└──────────────────────────────────────┘

Only one DAG section can be expanded at a time if that provides a cleaner UX.

The UI should dynamically create/remove DAG sections when the “Number of DAGs to Create” value changes.

For example:

* User enters 2 → show DAG 1 and DAG 2
* User changes to 5 → show DAG 1 through DAG 5
* User changes from 5 to 2 → retain DAG 1 and DAG 2 and safely remove DAG 3–5 from the active form state
* Avoid losing already-entered values unnecessarily when the count changes.

Add clear labels such as:

* DAG 1
* DAG 2
* DAG 3

Optionally show a small completion indicator for each DAG so the user can easily identify which DAG configuration is incomplete.

⸻

Do NOT create separate hardcoded variables such as:

dag1_name
dag2_name
dag3_name
dag4_name
dag5_name

The backend must use a dynamic/list-based structure.

Use a request-level object containing common Jira/request information and a list of DAG objects.

        },

            "dag_name": ...,

            "schedule": ...,
            "scheduling_configuration": ...,
            "tasks": [...],
            "task_arguments": [...]
        }
    ]

Use the actual existing field names from the current implementation rather than inventing new names unnecessarily.

8. Validation

Add validation for:

* Number of DAGs must be a valid positive integer.
* Every DAG must have the required DAG-level fields.
* Duplicate DAG names should be detected if duplicate names are currently not allowed.
* Validation errors should identify the specific DAG.

For example:

DAG 2: DAG Name is required.
DAG 4: Schedule is required.

Do not show generic errors such as:

Schedule is required.

when multiple DAGs exist.

The existing single-DAG use case must continue to work.

If:

the user should see essentially the same DAG configuration experience as today, while internally the data should still use:

dags[0]

This avoids having two completely different code paths.

                    INTAKE REQUEST
                          │
